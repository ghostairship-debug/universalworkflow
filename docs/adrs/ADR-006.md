# ADR-006 - Runtime Context Budget And Pruning Strategy

## Status

Accepted

## Context

The repository now has two live context-bearing runtime paths:

- compile-time state assembly can persist `domain_pack_resolution`, `memory_retrieval_preview`, and related run context
- the OpenAI-backed `RuntimeGateway` can turn that state into a short `runtime_brief`

Before `Pre-M8`, this context path had no explicit budget diagnostics or guard. That created two risks:

1. live-provider prompts could silently grow without any operator-visible signal
2. the repository might jump straight from "no guard at all" to a complex eviction/pruning engine too early

The pre-`M8` hardening goal is to make this path safe to evolve without expanding into a full context-management subsystem.

## Decision

The repository adopts a **diagnostics-first** context-budget strategy for pre-`M8`.

### 1. Compile/runtime state must expose a visible context-budget report

The runtime state payload should carry a small `context_budget` block that reports:

- section sizes for the main compile/runtime context contributors
- warning and hard limits
- prompt size when a live runtime brief is being assembled
- a simple `ok` / `warning` / `over_budget` status

### 2. Live runtime-brief assembly gets a conservative hard guard

The OpenAI-backed `RuntimeGateway` may refuse to create a runtime brief when the combined payload clearly exceeds the configured hard limit.

This is intentionally a narrow preflight, not a generalized token allocator.

### 3. No automatic pruning or eviction engine is introduced before `M8`

Pre-`M8` does **not** implement:

- automatic memory-item eviction
- dynamic domain-pack reduction
- multi-pass prompt compression
- token-provider-specific budgeting heuristics

If a payload is too large, the current system should surface diagnostics and fail clearly instead of mutating context implicitly.

## Consequences

Positive:

- runtime context growth is now visible
- live-provider failures can be explained with structured diagnostics
- the repository keeps a conservative, testable preflight without reopening architecture breadth

Tradeoffs:

- the current limits are character-based approximations, not model-true token counts
- operators may still need to manually reduce memory/domain context when a run exceeds the budget
- deeper pruning strategy remains deferred to a later cycle

## Follow-up

Future cycles may build on this ADR by adding:

- provider-aware token estimation
- explicit pruning plans
- memory/domain ranking rules
- richer runtime-brief compaction or prompt-shaping policies

Those changes should extend this ADR rather than bypassing it.
